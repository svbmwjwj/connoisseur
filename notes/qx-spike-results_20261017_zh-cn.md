###### 圈X 客户端检测试验结果

2026-10-17 在 `prod-us` 上搭了临时 REALITY 节点（端口 38443）和临时配置与报告地址（端口 38080），用一台 iPhone（圈X 1.8.1，iOS 27.0.1）实测。环境保留到 18 日早上测完锁屏后台执行，随后全部删除。

**结论一览**

| 测试项 | 结果 | 说明 |
| :--- | :--- | :--- |
| 远程配置与本地配置并存 | 通过 | `resource-tag-regex=^(self-built\|cnsr)$` 的策略组同时列出两边的节点 |
| 内置测速的返回格式 | 通过 | `{"ret":{"cnsr-test-1":[TCP毫秒, HTTP毫秒]}}`，失败项为 -1 |
| SNI 失配 | 通过 | 返回 `[180, -1]`，判定为握手失败 |
| TCP 阻断 | 通过 | 返回 `[-1, -1]`，判定为 IP 不通，通知送达 |
| 单条通知送达与跳转 | 通过 | 带 `open-url` 的通知能送达，点击能打开圈X |
| 同一次运行连发两条通知 | 失败 | 第二条被吞，正式版必须把多件事合并成一条通知 |
| 打开圈X 时自动更新配置 | 失败 | 打开 App 不会触发远程配置下载 |
| 点通知一键更新 | 通过 | 通知的 `open-url` 用 `quantumult-x:///add-resource?remote-resource=...`（同一地址、同一 tag），点开后圈X 提示更新，确认即下载新配置，不会产生重复资源 |
| 手动更新 | 通过 | 长按「风车」更新外部资源，会同时重新拉取远程配置和远程脚本 |
| 换 SNI 后选中状态 | 通过 | tag 不变时，策略组里选中的节点保留 |
| 配置地址出错 | 通过 | 返回 500 时圈X 显示更新失败，但保留原有节点，照常可用 |
| 锁屏后台执行 | 通过 | 10 月 17 日 22:00 到 18 日 9:40（北京时间）共 141 次检测，每 5 分钟一次，没有一次遗漏，夜间通知也能送达 |
| 单次误报 | 出现 | 18 日 0:30 有一次握手失败（TCP 正常、HTTP 失败），0:35 即恢复；只凭一次失败就换 SNI 会误换 |

**对正式设计的影响**

— 通知合并 — 一次检测只发一条通知，把状态变化和“配置已更新”写在同一条里。
— 持续提醒 — “配置已更新”不能只提醒一次：定时任务可能抢先消耗掉这次变化（试验中 11:30 的定时任务就这样），所以只要节点仍然连不上、服务器已有新配置，就要隔一段时间再提醒。
— 更新方式 — 通知用 `add-resource` 链接实现一键更新，用户只需点两下（点通知、确认更新）。
— 远程脚本会被缓存 — 圈X 会缓存远程脚本，更新外部资源时才一并刷新，所以检测脚本的升级要配合资源更新。
— 通知文案 — 要直接说结论，例如“节点 jp-1 连不上：SNI 可能被阻断，已通知服务器更换”，不出现 tcp-fail、毫秒数这类技术字样。
— 误报来源 — 刚加配置、节点尚未载入时运行检测，会拿不到测速结果，脚本要把这种情况当作“无结果”跳过，而不是判定失败。
— 加速确认是必要的 — 夜间出现过一次孤立的握手失败，5 分钟后自行恢复。设计里“失败后隔 3、2、1 分钟再测，3 次全失败才报告”正好能过滤掉这种情况。

试验环境已于 2026-10-18 清理：试验容器、临时服务、ufw 规则和临时目录都已删除，`prod-us` 原有的 `xray` 容器和 443 端口未受影响。
