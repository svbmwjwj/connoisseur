###### cnsr 重新设计（精简版）

本文档以帮助菜单为主线描述 cnsr 的新实现：先给出完整的 `cnsr -h` 输出，再逐条展开命令，其余机制挂在命令下面说明。上一版完整设计存档在同目录的 `cnsr-redesign-spec_zh-cn_bak_20261017.md`，本文以精简版为准。

**为什么要重做**

现有实现约 1 万行 Bash，审计后保留 134 条结论，去重后为 82 个问题，详见同目录的 `reliability-audit_20261016_zh-cn.md` 和 `reliability-issues_20261016_zh-cn.md`。核心问题有三类：

— 自愈看不到失效 — 所有检测都从服务器发出，看不到国内到节点之间的阻断。每次轮换还会重置 UUID 和密钥，所有客户端随之失效。
— 部署路径不可用 — 单台 `init` 每次都失败，`--detach` 什么都不部署，Lightsail 上的 `--harden` 一定锁死主机。
— SNI 候选来源不稳 — 每台节点只扫自己所在的 /22，稀疏网段筛完一个不剩，只能退回写死的大站备用池。

**目标**

只做两件事：

— 自动部署 — `cnsr add` 一条命令部署一台 Xray REALITY 节点，AWS 和小厂商走同一条流水线。
— SNI 失效后自动更换 — 你设备上的圈X 从国内视角发现 SNI 被封，节点自动换 SNI，你点两下就能用上新配置。

此外，节点配置和扫描结果都不出现在公开位置，也不使用第三方监控服务。测试通过后会新建公开仓库发布，任何人只要有一个托管在 Cloudflare 的域名就能用，不依赖你个人的环境。

**不做的事**

— 命令 — `list`、`status`、手动换 SNI、`client`、`update`、`pool`、`setup` 都砍掉，只保留 `add` 和 `rm`。凭据在第一次 `add` 时询问。
— 参数 — `--harden`、`--user`、`--port`、`--key`、`--detach` 都砍掉。加固按登录用户自动判断，其余在交互里问，或沿用已有的 SSH 别名。
— 批量部署 — 一次部署一台。
— 自动换 IP — IP 被封时只通知你。
— Telegram 通知 — 圈X 的本地通知已经覆盖。
— GitHub Actions 扫描和候选池 — 改为部署时在你的电脑上扫描。
— 节点自查和伪装站检查 — Xray 崩溃交给 Docker 自动重启；伪装站失效时，圈X 同样会测出握手失败。
— 检测心跳、历史记录、多设备佐证、知名度排名 — 首版都不做。
— 迁移旧节点 — 新版本从零部署，不迁移旧节点。新实现先在本地开发，将来发布到新建的公开仓库；旧的 `cnsr.cmd`、`cnsr.ps1` 不迁移，新版本原生支持 Windows。
— 圈X 以外的客户端检测 — 首版只做圈X。

**会让这次重做失败的情况**

— 加固把主机锁死。
— 换 SNI 后客户端拿不到新配置，或者换了之后反而连不上。
— 节点地址与 SNI 的对应关系、节点配置出现在任何公开的地方。
— 测量故障被当成 SNI 失效，引发反复轮换。
— 扫描让你的服务器或账号被厂商标记。

**使用前提**

— Cloudflare — 一个账号，以及一个托管在上面的域名。控制端和节点域名都挂在这个域名下。
— SSH agent — 钥匙放在任意 SSH agent 里，例如 Bitwarden、1Password 或系统自带的 ssh-agent。cnsr 不接触私钥。
— AWS（可选） — 只在用 `--aws` 时需要 access key。
— 圈X（可选） — 自动检测和换 SNI 依赖它。没有圈X 也能部署和使用节点，只是没有自动换 SNI。
— 直连的电脑 — 扫描要在你自己的电脑上直连进行，不能经过代理或云服务器（见第 7 节）。

**1. 帮助菜单**

`cnsr -h`（或不带参数运行 `cnsr`）的输出如下。这是用户可见的契约，措辞可以微调，但命令和参数必须一致。

```text
cnsr  自建 REALITY 节点：自动部署，SNI 失效时自动更换

用法  cnsr <命令> [参数]

命令
  add [别名]            添加一台节点；不带参数时逐项询问
      --aws <区域>      在 AWS Lightsail 新开一台（区域：jp、sg、us）
      --ip <IP>         接管一台已有服务器
  rm <别名>             删除节点；AWS 节点同时删除实例、释放静态 IP

对已有别名再次运行 add：续跑没完成的步骤、补充备选 SNI，并把节点更新到当前版本。

选项
  -h, --help            显示本帮助
  --version             显示版本
```

**2. add：交互与参数**

不带参数时按下面的顺序询问，参数给全了就不问。

1. 第一次运行 — 本机没有 Cloudflare token 时，询问 token 和要使用的域名，逐项验证权限。账号里已有 cnsr 控制端就直接接管，没有才部署（见第 11 节）。这一步可以开着代理。
2. 别名 — 只允许小写字母、数字、`-` 和 `_`，与你现有服务器的别名写法一致。别名已在控制端的节点清单里时，视为对已有节点重跑。
3. 服务器来源 — 已有服务器（输入 IP），还是新开 AWS。
4. AWS — 选区域 jp、sg、us。凭据先用 boto3 的默认凭据链（环境变量、`~/.aws`），都没有才询问 access key。规格和系统用默认值，不问。
5. 已有服务器 — 别名已在节点清单或 `~/.ssh/config` 里时，沿用其中的地址、用户、端口和钥匙。否则询问登录用户（默认 root）和 SSH 端口（默认 22）；root 密码由 OpenSSH 自己提示输入，cnsr 不经手、不保存。
6. 钥匙 — 取 SSH agent 里与别名同名的钥匙（按公钥注释匹配）。没有就列出 agent 里的全部公钥让你选，并建议你新建一把同名钥匙。

**3. add：部署流水线**

| 步骤 | 做什么 | 小厂商（`--ip`） | AWS（`--aws`） |
| :--- | :--- | :--- | :--- |
| 1. 拿到 IP | 确定节点的 IPv4，有公网 IPv6 一并记下 | 你给出 | 开 Lightsail 实例，分配静态 IP，绑定钥匙（见第 5 节） |
| 2. 连接并建解析 | SSH 别名先写 IP；连上后建随机前缀域名（见第 6 节） | 用 root 密码登录，装入公钥，立即用密钥重新登录确认 | 用 key pair 登录 `admin` |
| 3. 加固 | 见第 4 节 | 登录用户是 root 就自动加固，否则跳过 | 总是执行固定基线 |
| 4. 扫描候选 | 在你的电脑上扫描（见第 7 节） | 相同 | 相同 |
| 5. 定 SNI | 节点在本机验证，选 1 个使用，另存最多 10 个备选 | 相同 | 相同 |
| 6. 装 Xray | 装 Docker，按 compose 模板启动。生成 UUID、密钥和 shortId，先 `xray -test` 再启动，在节点本机验证握手，再由控制端从外部测 v4 的 443、由你电脑测 v6 的 443 能否连通 | 相同 | 相同 |
| 7. 装节点端服务 | 见第 10 节 | 相同 | 相同 |
| 8. 收尾 | 在控制端登记节点、写入配置行；SSH 别名切到域名；输出圈X 配置 | 相同 | 相同 |

各步骤的细节：

— 重跑 — 每一步先检查实际状态，已经符合就跳过，不符合就修正。中途失败时，修好问题再跑同一条命令即可。重跑不改变 UUID、密钥和当前 SNI。
— 失败即清理（AWS） — 第一次部署在 AWS 上中途失败、被 Ctrl-C 中断或终端被关掉（SIGHUP/SIGTERM 按 Ctrl-C 处理）时，按 `rm` 的方式删除这次建的实例、静态 IP、DNS 记录、SSH 别名和节点登记，删不掉的列出来让你用 `rm` 补删；之后重跑会重新开一台。实例名在创建之前、静态 IP 名在绑定之前就记进节点登记，所以中途被杀掉也不会留下 `rm` 找不到的计费资源。部署成功过的节点重跑失败时什么都不删，小厂商服务器也不删。
— 走代理时等你关代理 — 第一次部署到扫描这一步、发现走了代理时，不停下也不清理，等你关闭代理后重新检查（见第 7 节）。
— AWS 默认值 — 区域对照：`jp` 对应 `ap-northeast-1`，`sg` 对应 `ap-southeast-1`，`us` 对应 `us-west-2`，加区域只需补一行。规格 `nano_3_0`（双栈），系统默认 Debian 13，Lightsail 不提供时用 Debian 12。
— 连接失败 — 停下并说清卡在哪：端口不通、密钥被拒、密码错误、主机指纹不符，各给一句排查建议。不自动重试密码。
— 支持的系统 — `--ip` 只支持 Debian 12、13 和 Ubuntu 22.04、24.04，x86-64 架构。连上后先识别，不支持就停下；Ubuntu 22.10 以后改 SSH 端口要单独处理 `ssh.socket`。
— 动手之前先体检 — 第 2 步连上后、做任何改动之前，检查系统版本、443 是否空闲、除 SSH 外有没有其他监听端口、有没有正在运行的容器、有没有已有的防火墙规则。任何一项不像全新系统，就停下并列出发现，不做任何改动；cnsr 只接管全新的服务器，不改端口、不碰已有服务。
— compose 模板 — 沿用现有的 `templates/compose.yml.template`：镜像版本固定、`restart: unless-stopped`、日志轮转、开启 IPv6 网络。
— 收尾输出 — 每次成功都在终端输出圈X 需要的几行（见第 9 节），替代被砍掉的 `client` 命令。第一次部署时提示你粘贴到每台设备，分享给别人时把同样几行发给对方。

**4. 加固**

小厂商在登录用户是 root 时自动执行左列。登录用户已经是普通用户，说明这台机器配置过，跳过加固。AWS 总是执行右列。

| 项目 | 小厂商（root 登录时） | AWS Lightsail |
| :--- | :--- | :--- |
| 登录账户 | 新建普通用户 `admin`，免密 sudo，装入你的公钥 | 镜像自带的 `admin` |
| SSH 端口 | 改为随机高位端口 | 保持 22 |
| 改端口的顺序 | 新旧端口同时监听 → 防火墙放行新端口 → 用新端口和新用户实际登录成功 → 再关闭 22、禁用 root 和密码登录。任何一步失败就回滚到改动之前 | 不涉及 |
| 密码登录、root 登录 | 关闭 | 镜像默认已关闭，只核验 |
| 防火墙 | 主机防火墙只放行新 SSH 端口和 443 | Lightsail 云防火墙的 IPv4、IPv6 规则都只放 22 和 443，关掉默认开着的 80；不装主机防火墙 |
| 防爆破 | fail2ban，监控新 SSH 端口 | 不需要 |
| 自动安全更新 | 开启 | 开启 |
| 应急进入 | 厂商网页 VNC 控制台。cnsr 为新用户生成控制台密码并显示，你存进密码管理器、输入“已保存”后，cnsr 才继续关闭 22 | Lightsail 网页版 SSH |
| sshd 配置方式 | 写独立的 drop-in 文件，用 `sshd -T` 核验最终生效值 | 只核验 |
| 收尾 | `~/.ssh/config` 里的别名改为新端口和新用户 | 不涉及 |

443 的放行范围与 compose 模板的端口映射一致（模板同时映射了 TCP 和 UDP）。cnsr 不碰任何密码库，控制台密码只由你保存。

**5. 密钥与 SSH 别名**

— 私钥只在 agent 里 — cnsr 全程不接触私钥，只通过 SSH agent 使用钥匙。
— 一台服务器一把钥匙 — 默认约定沿用你现在的习惯：钥匙以别名命名，公钥放在 `~/.ssh/pub/<别名>.pub`。公钥文件不存在时，cnsr 从 agent 导出写入。
— AWS key pair — Lightsail 的 key pair 按区域存放，所以按区域分别判断，并且按指纹而不是名字比对。不使用 `LightsailDefaultKeyPair`。
  1. 该区域已有指纹相同的 key pair（不管叫什么名字）→ 直接复用。
  2. 该区域有同名但指纹不同的 → 停下说明冲突，不覆盖。
  3. 都没有 → 以钥匙的名字导入，再绑定到新实例。
— 指纹格式 — 比对时兼容 Lightsail 的两种格式：ED25519 是带 `=` 结尾的 SHA256 base64，RSA 是冒号分隔的十六进制。
— 小厂商 — root 密码登录后写入 `authorized_keys`，立即用密钥重新登录确认可用。
— 别名内容 — `IdentityAgent` 指向你用的 agent（第一次运行时检测，检测不到就问你），`IdentityFile` 指向这把钥匙的 `.pub`，并设置 `IdentitiesOnly yes`，避免 agent 里钥匙太多被服务器拒绝。
— 别名的生命周期 — 部署过程中 `HostName` 写 IP，收尾时切到域名（见第 6 节）。部署完成后别名保留，供你排查问题和手动升级；`rm` 时删除。
— 换电脑 — 在新电脑上重跑 `add <别名>`，会按控制端的节点清单重新生成别名。
— 只改自己的条目 — 只改与别名同名的 `Host` 块，写之前备份原文件，不动其他内容。

**6. 域名解析**

保留域名是为了让一条圈X 配置同时覆盖 v4 和 v6，并且分享出去的配置里不直接出现 IP。

— 记录 — 每台节点一个随机前缀子域名，形如 `edge-cache-v534.<你的域名>`，灰云，TTL 1 分钟，备注写 `cnsr node <别名>`，在 Cloudflare 面板里一眼看出记录属于哪台节点。节点有公网 IPv6 时同时建 A 和 AAAA，否则只建 A。重跑 `add` 时给没有备注的旧记录补上，别人写过的备注不动。控制端 Worker 的自定义域名记录由 Cloudflare 托管，绑定接口没有备注字段，不加。
— 用在哪 — 圈X 配置行和 SSH 别名都写域名。
— 部署全程用 IP — 整个 `add` 过程中，SSH 一律直连 IP，不依赖解析。
— 尽早建、建之前不查 — 第 2 步就建好记录，到收尾之前都不查这个名字。名字是随机新生成的，建之前没人查过，就不会有“查不到”的结果被缓存。
— v6 不通时 — 第 6 步由你电脑从外部测 v6 的 443（控制端 Worker 连不了 IPv6，见第 15 节）。只有电脑确实能上 IPv6（能连通阿里、Cloudflare 或 Google 公共 DNS 的 v6 443；阿里排在最前，大陆网络也能连）而节点不应答时，才删除 AAAA 记录并提示你，节点只走 v4；电脑没有 IPv6，或开着 TUN 代理（DNS 返回假地址）时测不准，AAAA 保持现状并提示你没能验证。已经没有 AAAA 的节点再次测不通时只记一行日志，不重复警告。节点从本机连自己的公网地址，不经过云防火墙和上游路由，测不出 v6 的实际问题，所以要从外部测。
— 配置行一开始就写域名 — 写进控制端之前，先用公共 DNS 确认 A 和 AAAA 都查得到。这样以后不需要为改地址再更新一次配置。
— 收尾时切 SSH 别名 — 先确认你电脑上解析出的地址和节点一致、用域名能 SSH 登录，再把别名从 IP 切到域名。最多等 2 分钟；仍不行就保留 IP，部署照常完成并提示你，下次重跑 `add` 时再检查和切换。
— 删除 — `rm` 时删掉这台节点的记录。你账号里旧版建过的其他记录，cnsr 不动。

**7. 候选扫描与选 SNI**

扫描在你的电脑上进行。XTLS 官方的 RealiTLScanner 建议在本地运行，因为在云服务器上扫描可能被厂商标记，大多数厂商的服务条款也禁止扫描[^1]。

— 扫描工具 — RealiTLScanner 的发布文件没有 macOS 版本，所以 cnsr 用 Python 实现同样的探测：不带 SNI 按 IP 握手，只收 TLS 1.3 加 h2，读出证书域名。三个平台通用，不用下载二进制。
— 必须直连 — 扫描前检查这台电脑有没有走代理，两项都要满足：一是本机 DNS 没有把域名解析成 `198.18.0.0/15` 里的地址（圈X、Surge、Clash 等 TUN 模式代理的虚拟地址，公网 DNS 不会返回）；二是国内回显（`4.ipw.cn`，不通时用 `ipv4.ddnspod.com`）看到的出口，和节点从 SSH 会话的 `SSH_CLIENT` 看到的来源地址一致。扫描只在节点的 /20 里进行，第二项证明扫描与 SSH 走同一条路。走代理时请你关闭代理后重新检查，已开的实例保留。2026-10-18 实测：圈X 开着时连国内回显都走 `prod-sg`，只比较地址会误判为直连，所以加了第一项。
— 扫描范围 — 节点 IPv4 所在的 /20，排除节点自己所在的 /22，只扫 IPv4 的 443 端口。速率保持温和，具体线程数和超时由实现决定。
— 本机初筛 — TLS 1.3、h2、X25519；证书不是自签名、不是 Cloudflare Origin 证书、不是 localhost。
— 信誉过滤 — 全自动，不做人工审核，不用知名度排名：
  — 排除动态域名后缀，如 duckdns.org、`*.eu.org`、qzz.io，维护成一张表。
  — 排除名字里含代理面板和测试字样的，如 panel、xui、alist、frp、v2ray、stg、staging、dev、test、demo。
  — 排除低信誉顶级域（沿用现有那张表）。
  — 排除别人的节点：证书是知名大站、IP 却不属于该大站的，例如小厂商 IP 上出现 apple.com。
— 被墙域名 — 按 IP 扫描时不带 SNI，挡不住按 SNI 封锁的域名。所以对过滤后的候选，再从你电脑上带 SNI 握手一次，握不上就排除。IP 被墙的站点在扫描时本来就连不上。
— 节点验证 — 把初筛结果（证书域名和扫到的 IP）交给节点。节点用 curl 在本机逐个检查 TLS 1.3、h2、X25519、证书有效和握手延迟，按延迟排序，选第 1 个使用，其余全部存为备选（最多 30 个）。邻居和备用域名都没有通过的就停下，不盲选（用户，D-010）。
— 候选取法 — 按 /22 轮流取满 30 个，不按 IP 升序取前 30 个：有的厂商把同一个 /20 里的 /22 走不同的路由，节点可能整段连不通（用户，2026-11-24）。
— 备用域名 — 合格的邻居不足以凑够 10 个备选时，从代码里的大厂域名清单（按节点所在国家，没有的用通用清单）补足；邻居一个都不合格时首选也从清单取（用户，D-010）。走和邻居相同的检查，永远排在邻居后面，清单内自有网络的在前、CDN 在后，因为 REALITY 会把陌生人的连接转发给目标站（Claude）。备选带 `pool` 标记，换 SNI 前由节点重新解析（Claude）。
— 排除别人的节点（补充）— 节点解析候选域名，结果既不含扫到的地址、也不含同一家服务商地址（按反向域名比较）的排到最后、带 `foreign` 标记，不删除（用户：排到最后，D-012；判定方法与重排时机 Claude）。
— 伪装目标 — Xray 的 `dest` 写扫到的邻居 IP 加 443，`serverNames` 写它的证书域名。伪装流量真正落在同一网段的邻居上，不依赖域名解析。
— 备选只是候选，不是存货 — 备选是部署那天筛出来的，等到换 SNI 时可能已经过了几个月。所以换之前一律现场复验，过时的当场淘汰，见第 10 节（2026-10-19 决定）。
— 补充备选 — 只有备选全部在复验中被淘汰时，才通知你在电脑上重跑 `cnsr add <别名>`，重新扫描并补满备选。
— 扫描只能在你的电脑上 — 2026-10-19 逐一排除了其他扫描地点：节点和其他云服务器（含阿里云）违反厂商条款，云盾一类的检测会标记对外扫描；GitHub Actions 的托管 runner 不得用于与软件项目的开发、测试、部署、发布无关的活动，也不得当作 serverless 后端，而且在国外；Censys、Shodan 等被动数据源要付费或注册，你不接受；圈X 脚本只有 `$task.fetch`，不能按 IP 不带 SNI 握手，也读不到证书，做不了发现。调研见 `.notes/reports/被动 TLS 数据源对比.md`（工作树内）。
**8. rm**

1. 列出将删除的内容，要求你输入别名确认。确认后先把节点的配置行从订阅里撤下，再开始删，这样删到一半失败时，设备也不会继续拿到这台节点（2026-10-19）。
2. AWS 节点 — 删除实例，释放静态 IP。key pair 保留，同区域的其他实例可能还在用。
3. 删除 DNS 记录、控制端里的节点登记（配置行和节点 token）、SSH 别名，最后从控制端的节点清单移除。
4. 小厂商节点 — 服务器本身不动。节点端服务在 token 失效后（控制端返回 401）自行停止轮询。

`~/.ssh/pub/<别名>.pub` 和 agent 里的钥匙都保留。某一步失败时继续执行后面能做的步骤，最后列出没删干净的项，重跑 `rm` 可以补删。

— 残留的换 SNI 状态 — `rm` 之后约一分钟内，设备的报告可能凭控制端缓存里的旧记录写回 `state:<别名>`。之后用同一个别名新建节点时，`add` 先删掉这个残留状态，新节点不会一上来就换 SNI 或进入暂停期（2026-10-19）。

**9. 自动换 SNI：圈X 一侧**

`add` 收尾时输出的内容，每台设备粘贴一次：

```text
[server_remote]
https://<控制端域名>/<客户端 token>/cnsr.snippet, tag=cnsr, update-interval=86400, opt-parser=false, enabled=true

[filter_local]
host, <控制端域名>, direct

[task_local]
* * * * * https://<控制端域名>/<客户端 token>/check.js, tag=cnsr 节点检测, enabled=true
event-interaction https://<控制端域名>/<客户端 token>/check-ui.js, tag=cnsr 检测, enabled=true
```

同时提示把 `cnsr` 加进策略组的 `resource-tag-regex`，例如 `^(manual|cnsr)$`。cnsr 只管远程资源 `cnsr`，从不碰手动配置的节点，手动维护的片段照旧由你自己同步。

分享节点时把同样几行发给对方，对方也会收到通知，也参与检测。

**检测脚本（每分钟唤醒）**

— 节奏 — 没到时间就只读本地记录后退出，不发网络请求。平时每小时真正测一次。
— 先确认网络 — 用直连访问一个国内网站，不通就静默退出。
— 测速 — 对远程资源 `cnsr` 里的每个节点和你手动配置的其他节点调用圈X 内置测速（`url_latency_benchmark`），得到 TCP 和 HTTP 两个值。
— 分类 — TCP 失败判为“连不上”；TCP 成功但 HTTP 失败判为“握手失败”；拿不到结果就跳过，不算失败。
— 加速确认 — 某个节点握手失败后，隔 3 分钟、再隔 2 分钟、再隔 1 分钟各测一次。3 次全失败、并且至少有一个其他节点正常，才确认并用直连报告控制端。
— 只报告最新配置 — 每次报告都带上圈X 实际加载的该节点 SNI，控制端据此忽略过期的报告。读法待实测；读不出来时退一步：设备看到有新配置、而自己还没用新配置测通过，就只提醒更新，不报告。
— 只有一个节点时 — 无法排除你自己网络的问题，自动检测不报告，只通知你，你可以用长按检测确认。
— 你的网络问题 — 所有节点都失败时，视为你当前网络的问题，不报告也不通知。
— 连不上 — 只通知你，不触发换 SNI。同一个状态只通知一次。
— 等新配置 — 报告后进入快速模式，每分钟查一次控制端的状态。发现新配置就通知你；节点仍连不上而配置已更新时，每 30 分钟再提醒一次。
— 测通回报 — 快速模式下，节点用新配置测通后向控制端回报一次，然后回到每小时的节奏。节点处于暂停期时，每小时检测测通也回报：换 SNI 后旧配置一定连不上，所以暂停期里的测通必定是用新配置测的（2026-10-19）。长按检测和每小时检测各自整段写回状态，每小时检测保存时保留长按在它运行期间开启的快速模式；下一次每小时检测的时间在测速之前就先存下。
— 通知 — 一次运行最多发一条，多件事合并写进去。配置更新的通知带 `quantumult-x:///add-resource?...` 链接，你点通知、在圈X 里确认即可更新。
— 文案 — 直接说结论，例如“节点 jp-1 的 SNI 可能被封，服务器已换用新 SNI，点此更新”，不出现 tcp-fail、毫秒数这类字样。
— 锁屏 — 设备睡眠时检测暂停，醒来后继续，可以接受。

**长按检测（交互脚本）**

— 触发 — 在策略页长按节点，选“cnsr 检测”。脚本通过 `$environment.params` 拿到所选节点[^2]。
— 快速确认 — 连测 3 次，间隔约 10 秒。都是握手失败、并且直连国内网站正常，就马上报告，并让检测脚本进入快速模式。手动触发说明你已经感觉到问题，所以不要求“其他节点正常”。
— 配置过期时 — 已加载的不是最新配置，就提示你先更新，不报告。
— 结果 — 在交互界面里直接显示结论。

**10. 自动换 SNI：节点与控制端**

1. 控制端收到报告，为该节点记一个换 SNI 请求。节点处于暂停期、或者报告里的 SNI 不是当前 SNI 时，忽略报告。
2. 节点端服务每 15 秒查一次有没有请求。
3. 有请求时按顺序现场复验备选，两关都过才用，不合格的丢掉、换下一个：
   — 服务器端 — 节点在本机重新检查 TLS 1.3、h2、X25519、证书有效和握手延迟（现有逻辑）。只连这一个网站，不是扫描。
   — 国内一侧 — 节点请 Globalping 的大陆探针（免费、匿名，每小时 250 次）对这个域名带 SNI 访问一次，看从国内能不能握手成功，排除按 SNI 被墙的。测量结果公开，但只涉及别人的网站，不含节点 IP。探针不在线、超出额度或接口出错时，这一关记为“没测”，只凭服务器端结果决定，并写进节点日志（`journalctl -u cnsr-rotate`）；不记成事件，因为控制端存下的事件没有地方显示，多写一次 KV 没有用处（2026-10-19）；换上后若仍被墙，客户端会照常再报告。具体接口和判定标准由实现者实测后确定（见第 15 节待实测项）。
4. 只改 `dest` 和 `serverNames`，UUID、密钥和 shortId 不变。先 `xray -test` 再重启容器，在本机验证握手；失败就回滚到旧配置，换下一个备选。
5. 成功后把新配置行写回控制端。控制端更新远程资源的内容，并让该节点进入暂停期。
6. 备选全部在复验中被淘汰时，保持旧配置，向控制端报告“备选用完”。圈X 下次运行时通知你：备选都已失效，在电脑上重跑 `cnsr add <别名>` 重新扫描。

— 暂停期 — 换完后暂停自动换，直到有设备用新配置测通。24 小时内都没有设备测通，说明新 SNI 可能也被封了，这时允许再换一次，并在通知里提醒你。
— 确认过的失败 — 长按检测在你按提示更新之后、或这台设备测通过当前版本之后再失败，会带上“已确认”。暂停开始满 10 分钟后，控制端接受这种报告，不必等 24 小时；它触发的换 SNI 又开始新的暂停，所以每个暂停最多一次（2026-10-19）。
— 读不出已加载的 SNI 时 — 按第 9 节的退路，没有设备会为新配置报告失败，所以 24 小时兜底改为通知你用长按检测手动触发。
— 响应时间 — 确认后大约 1–2 分钟收到通知：报告后节点 15 秒内取到请求，换 SNI 约半分钟，圈X 下一分钟发现新配置。
— 控制端同步 — KV 的跨机房同步可能有几十秒延迟。实测影响明显时改用 Durable Object，由实现者决定。

**节点端服务**

— 运行方式 — 常驻的 systemd 服务，单实例运行，只做换 SNI 这一件事。
— 依赖 — curl、jq 和 docker，部署时安装。依赖缺失或测量出错时只报告错误，不换 SNI。
— 加固的 ufw 端口 — 加固打开过的新 SSH 端口记在 `/opt/cnsr/.ufw-ports-by-cnsr`。中断后重跑换了新端口时，旧端口的放行规则会被删掉；完整回滚时删掉记录里的所有端口。关闭 22 端口那一步若在启动自动恢复计时器之前就失败（什么都没改），cnsr 不再白等 200 秒（2026-10-19）。
— 停止 — 收到 401（节点已被 `rm`）时停止轮询，并留下 `/opt/cnsr/stopped`；systemd 单元以它为条件，重启后不再启动。重新 `add` 时删掉它。
— 节点自身的故障 — 备选没通过本机验证或 REALITY 自检时，先确认节点自己能上外网（访问 gstatic 的 204）。节点连不上外网、或自检程序本身没能运行（客户端容器起不来、端口被占）时，不算备选的错：备选放回列表开头，按“换 SNI 失败”报告，一小时后再试，不会把备选一个个耗光（2026-10-19）。
— 更新 — 不从 GitHub 自动拉取任何东西，节点脚本只在 `add` 时下发。

**11. 控制端**

控制端是一个 Cloudflare Worker，配一个 KV，挂在你域名下的一个随机前缀子域名上；`workers.dev` 在国内基本不通，所以必须用自有域名。第一次 `add` 时由 cnsr 通过 Cloudflare API 部署，账号里已有就直接接管，重跑 `add` 时更新到当前版本。

控制端也是唯一的状态来源：节点清单（别名、来源、实例名、静态 IP 名、域名、DNS 记录 ID、SSH 用户、端口和钥匙名）和各种 token 都存在 KV 里。cnsr 通过 Cloudflare API 直接读写 KV 来登记、删除节点和签发节点 token，所以 Cloudflare token 是唯一的根凭据，换一台电脑填上它就能接管全部节点。

| 接口 | 谁调用 | 作用 |
| :--- | :--- | :--- |
| `GET /<客户端 token>/cnsr.snippet` | 圈X | 返回所有节点的配置行 |
| `GET /<客户端 token>/check.js`、`check-ui.js` | 圈X | 返回检测脚本和长按检测脚本，节点列表已填好 |
| `GET /<客户端 token>/status` | 圈X 脚本 | 返回各节点的配置版本、是否在暂停期、备选是否用完 |
| `POST /<客户端 token>/report` | 圈X 脚本 | 报告“握手失败已确认”或“新配置已测通” |
| `GET /node/<别名>/task` | 节点 | 查询有没有换 SNI 请求 |
| `PUT /node/<别名>/line` | 节点 | 换完后写回新配置行 |
| `POST /node/<别名>/event` | 节点 | 报告备选用完、换 SNI 失败等事件 |
| `POST /admin/probe` | cnsr | 从外部测节点某个地址的 443 能否连通 |

— 节点 token — 每台节点一个，只能读写自己的条目。一台节点被攻破，不影响其他节点。
— 客户端 token — 一个，你和你分享的人共用。首版不支持单独作废某一个人。
— 节点用户 — 记录在 `node:<别名>` 的 `users` 里（名字和 UUID），Xray 配置的 `clients` 第一个是你自己，后面是用户；重跑 `cnsr up` 按记录重新生成（用户：添加和收回，D-011；其余 Claude）。改用户时先停换 SNI 服务，只改 `clients`，过 `xray -test` 后由节点上的 `apply-config.sh`（systemd 运行）重启、验证握手、失败恢复旧配置，cnsr 重连后读结果：这台电脑可能正经过节点自己的 Xray 连节点，重启会切断连接（Claude，2026-11-24 真机验证发现）。
— 重启 Xray — `cnsr up` 在配置或 `compose.yml` 有变化时用同一个 `apply-config.sh`，换 SNI 服务照旧停到最后一步；握手失败时恢复旧配置再报错（用户：改成同样做法；其余 Claude，2026-11-24）。
— 管理 token — 存在 KV 里，只用于 `/admin/probe`，有 Cloudflare token 就能读到。
— 失败即拒绝 — 缺少任何 token 配置时拒绝请求，不放行。
— Cloudflare token 的权限 — DNS 编辑、Workers 脚本编辑、Workers KV 编辑，以及绑定自定义域名所需的权限。第一次运行时逐项验证，缺哪项就说明哪项。
— 免费额度 — 写入只发生在报告和换 SNI 时，远低于上限。每台节点轮询一天约 5,760 次请求，每次请求读 3 个 KV 键（`meta:control`、`node:`、`state:`），一天约 1.7 万次 KV 读取；免费套餐每天 10 万次 KV 读取，扣掉圈X 的用量大约只够 5 台节点（2026-10-19 复核，原先按请求数算的“约 15 台”偏高）。
— list 额度 — 免费套餐的 KV list 另有每天 1,000 次的上限。旧版 Worker 每次 `status` 和订阅请求都 list 一次 `node:` 前缀，圈X 快速模式每分钟查一次 `status`，一台设备一天就能用完（2026-10-20 被封锁 06:22–08:00）。现在 cnsr 维护节点清单键 `index:nodes`（别名的 JSON 数组）：`add` 先写清单再写记录，结束前再补写一次本节点；`rm` 先删记录再改清单。清单缺失或损坏时，cnsr 用一次 list 从现有 `node:` 记录重建。Worker 只读清单并跳过读不到记录的别名，没有清单的老控制端才退回 list；`status` 因此多 1 次读取，仍在读取额度内（2026-10-20）。

**12. 节点上有什么**

— Xray 容器 — 由 compose 管理，沿用现有模板。
— 节点端服务 — 一个常驻脚本加对应的 systemd 单元。
— 配置文件 — 节点 token、控制端地址、备选 SNI 列表，权限 600。不保存 Cloudflare 或 AWS 的凭据。
— 不装的东西 — 不装 cron 任务，不从 GitHub 拉取脚本。

**13. 本机文件与平台支持**

— 凭据 — 只有 Cloudflare token 和 AWS access key，存在 cnsr 配置目录下的 `secrets.env`，仅当前用户可读。
— 节点清单 — 存在控制端，本机不保存（见第 11 节）。

cnsr 的本机部分要在 macOS、Windows 和 Linux 上都能用，节点端始终是 Linux 服务器。

| 项目 | macOS | Windows | Linux |
| :--- | :--- | :--- | :--- |
| 安装 | `uv tool install` | 同左 | 同左 |
| SSH | 系统自带的 OpenSSH | Windows 10 起自带的 OpenSSH 客户端 | 系统自带的 OpenSSH |
| SSH agent | agent 的 Unix socket，如 Bitwarden、1Password 或系统 ssh-agent | OpenSSH 的命名管道 `\\.\pipe\openssh-ssh-agent`，Bitwarden 和 1Password 都用它 | agent 的 Unix socket |
| SSH 配置文件 | `~/.ssh/config` | `%USERPROFILE%\.ssh\config` | `~/.ssh/config` |
| cnsr 配置目录 | `~/.config/cnsr/` | `%APPDATA%\cnsr\` | `~/.config/cnsr/`（遵守 `XDG_CONFIG_HOME`） |
| 凭据文件权限 | 600 | 用 ACL 限制为仅当前用户可读 | 600 |
| 终端输出 | UTF-8 | 强制 UTF-8，兼容旧版控制台 | UTF-8 |

— 不依赖 shell — 本机代码不调用 bash、sed、awk，文本处理都在 Python 里完成。SSH 和 SCP 用参数列表调用，不拼接命令字符串。
— 路径与换行 — 路径一律用 `pathlib`。读取任何文件都容忍 CRLF（包括 `.env` 里 Windows 换行留下的 `\r`），写出的文件统一用 LF。
— SSH 选项 — 不使用 Windows 上不可靠的 ControlMaster 连接复用，并设 `ControlPath=none`：否则你自己开着的 SSH 主连接会被借用，验证“新登录能用”时就测不出真实情况。只跑 `true` 的登录检查超时，算作 SSH 失败，可以重试。服务器脚本在服务器上用 `timeout` 自己限时，比本机早 15 秒结束，因为本机杀掉 ssh 并不会停下服务器上的脚本；加固的三个脚本还共用一把锁（`/run/cnsr-harden.lock`），回滚不会和还在跑的上一步重叠。
— SSH 配置文件 — 新别名块插在第一个也适用于这个别名的块（`Host *`、匹配的通配符或任何 `Match`）之前，连同它上面的注释一起让出位置，因为 ssh 每个选项只取第一次出现的值；没有这样的块才追加到末尾。读改写全程持有 `~/.ssh/config_lock_cnsr` 文件锁，替换前先 fsync（2026-10-19）。

**2026-10-19 Globalping 国内检验实测**

— 可用性 — 从东京节点匿名调用，不用注册；大陆在线探针 63 个，有中国移动、中国电信、腾讯云、华为云。限额每小时 250 次，一次检验用 3 个探针占 3 次。
— 测量方式 — `type: http`、`protocol: HTTPS`，`target` 写邻居 IP，`request.host` 写候选域名，探针就以它为 SNI 握手，不经过国内 DNS，所以不受 DNS 污染影响。约 2 秒出结果。
— 正常的候选 — `miyashita-park.tokyo`（18.177.229.178）：广州、上海、北京三个探针都握手成功，TLSv1.3，拿到它的证书。HTTP 状态码是对方网站的事，不看。
— 被墙的 SNI — 同一 IP 带 `www.facebook.com`：中国移动北京、中国电信广州、腾讯云广州三个探针全部 `read ECONNRESET`。
— 判定 — 3 个探针里至少 2 个握手成功算通过；至少 2 个在 TCP 连上之后、TLS 握手中被切断（重置、握手超时、“socket hang up”）算被墙；其余（包括接口出错、额度用完、探针不够）算“没测”。TCP 阶段就失败的不算被墙：只有节点会连邻居，国内连不上邻居与 SNI 无关。
— 时间上限 — 一次换 SNI 里所有国内检验合计最多 90 秒，之后的备选只凭本机验证；单次检验最多等 8 轮，而且每个请求和轮询都不超过剩下的时间，所以这 90 秒是硬上限（2026-10-19）。
— 隐私 — 请求从节点地址发出，用 curl 默认的 User-Agent，不带 cnsr 字样。测量内容只有邻居 IP 和候选域名。

— 测试资源 — AWS 用临时 Lightsail（东京、`cnsr-test-` 前缀、`jp-key`），小厂商真机由你安排。
— 失败即清理 — AWS 上第一次部署失败时自动删除这次建的资源，不留着计费等重跑（2026-10-18 真机测试时决定，细节见第 3 节）。
— 选择题 — 用方向键选择，不输入数字（2026-10-18）。
— 备选现场复验 — 备选不再直接拿来用：换 SNI 前节点现场复验，再由 Globalping 大陆探针从国内检验；扫描仍只在你的电脑上做，部署时保留全部合格候选（2026-10-19，第 7、10 节）。

**17. 我做的决定（请过目）**

— 伪装目标 — `dest` 写扫到的邻居 IP，`serverNames` 写它的证书域名。
— 动手前体检 — `--ip` 只接管全新的服务器，发现其他服务、容器或防火墙规则就停下，不做任何改动。
— 外部探测 — v4 由控制端从外部测，v6 由你电脑测；只有确实测到 v6 不通才不建 AAAA，测不了时保持现状。
— 扫描细节 — 范围是节点所在的 /20、排除自己的 /22，只扫 IPv4；备选最多 10 个；信誉过滤全自动，规则见第 7 节。
— 直连检查 — 扫描前查本机 DNS 有没有代理的虚拟地址，并比对国内回显看到的出口和节点看到的来源地址；走代理时等你关闭代理（第 7 节）。
— 扫描工具 — RealiTLScanner 没有 macOS 版本，cnsr 用 Python 实现同样的探测。被墙域名改为从你电脑上带 SNI 握手来排除，节点验证改用 curl，不再依赖 reality-checker。
— AWS 凭据 — 先用 boto3 的默认凭据链，都没有才询问。
— 只有一个节点时 — 自动检测不报告、只通知；长按检测不要求“其他节点正常”。
— 你的网络问题 — 所有节点都失败时不通知。上一版是持续 1 小时后通知一次，这次砍掉了。
— 暂停期 — 由控制端执行，节点端不用管。
— 重跑 `add` — 每一步按实际状态补齐，节点脚本、Xray 版本和控制端也会更新到当前版本，但不改 UUID、密钥和当前 SNI。这在一定程度上替代了被砍掉的 `update`。
— AWS 系统 — 默认 Debian 13，Lightsail 不提供时退回 Debian 12。Debian 13 已发布一年多，Debian 12 已转入长期支持。
— 小厂商新用户 — 用户名 `admin`，与 AWS 一致，免密 sudo。
— 控制台密码 — cnsr 生成并显示，你自己存进密码管理器，cnsr 不碰任何密码库。
— 控制端 — 挂在随机前缀子域名上。客户端 token 共用一个，首版不能单独作废某一个人。
— 帮助 — `-h` 和 `--version` 作为选项，不算命令。
— `add` 的输出 — 每次成功都输出圈X 配置，替代 `client`。
— `rm` 的容错 — 某一步失败时继续执行后面的步骤，最后列出没删干净的项。
— 状态存放 — 节点清单和各种 token 都存在控制端 KV，本机只存 Cloudflare token 和 AWS 密钥。换电脑时填上 Cloudflare token 就能接管，路径见第 13 节。
— 管理方式 — cnsr 通过 Cloudflare API 直接读写 KV，管理接口只剩外部探测一个。
— SSH agent — 任何 agent 都行；钥匙命名和公钥位置沿用你的习惯，作为默认约定。— 支持的系统 — `--ip` 只支持 Debian 12、13 和 Ubuntu 22.04、24.04，x86-64。
— 界面语言 — CLI 只做中文。
— 技术选型 — 见第 14 节。
